# 2.6 — Section Readiness Score

A per-section **Readiness** score (1–10) returned by Claude alongside the existing gap analysis, surfaced as a red-to-green segmented bar inside each `BriefSectionCard` and on the Step 6 Review view. Extends [[Gap Analysis]] without changing its core flow.

> [!info] Design intent
> The score gives users an at-a-glance signal of *how usable* each section is, separate from the binary "has gaps / no gaps" view. It runs as part of the same Claude call that produces gaps — no extra round-trip, no new prompt.

## Overview

Today, [[Gap Analysis]] tells users *what is missing* but not *how close a section is to being ready*. A section can technically have zero gaps yet still be thin or generic; conversely a section may have a "nice-to-have" gap and otherwise be excellent. The Readiness score fills that interpretive gap.

The score is:
- **Produced by Claude** as part of the existing `GAP_ANALYSIS_TOOL` tool-use response.
- **Persisted** on `brief_sections` so it survives page reloads and is available on Step 6 without a re-fetch.
- **Visualized** as a 10-segment red-to-green gradient bar below each section title.
- **Marked stale** (dimmed) when section content has been edited after the last analysis ran.

## Goals

- Give users a fast visual heuristic for which sections still need work.
- Reuse the existing Claude call — zero added API cost per analysis.
- Make staleness obvious so users know when to re-run analysis.
- Persist scores per section in the database for durability across sessions.

## Non-Goals

- No animation or transitions on the bar (static rendering only).
- No score for the *overall brief* — section-level only in this iteration.
- No historical tracking of score over time (later, possibly via [[Version History]]).
- No automatic re-analysis on edit — user still clicks "Re-check gaps".
- No score breakdown by sub-criterion (completeness vs specificity etc.) — single integer only.

## UX Design

### `ReadinessBar` component

A horizontal 10-segment bar rendered **below the section title, above the textarea/content** in `BriefSectionCard`. Also appears on the Step 6 Review view next to each section summary.

> [!info] Visual spec
> - 10 equal-width segments laid out in a flex row.
> - Color gradient: segment 1 = red, segment 10 = green, smooth ramp through amber in the middle (use HSL hue from ~0° to ~120°, or a 10-stop predefined palette).
> - Segments 1..N are filled (where N = `readiness_score`); segments N+1..10 are rendered at low opacity / neutral.
> - Label: the word **"Readiness"** plus the numeric score (e.g. `Readiness 7/10`) shown to the side or above.
> - 10 = fully ready / actionable (best). 1 = risky / incomplete (worst).

### Empty / unscored state

- When `hasAnalyzed === false` **or** `readiness_score IS NULL`, the bar is **hidden entirely**. No placeholder, no zero-state bar.
- This mirrors the existing rule that inline gap hints only appear after analysis has run.

### Stale state

- When the section's `updated_at` is later than its `score_analyzed_at`, the bar renders at **~30–40% opacity** (`opacity-40`) with a small clock or refresh icon and a tooltip: *"Re-analyze to update"*.
- The score is not hidden — users still see the last known value, dimmed.

## Data Model

> [!info] Schema change
> Two new nullable columns on `brief_sections`. No new table.

| Column | Type | Notes |
|---|---|---|
| `readiness_score` | `INTEGER NULL` | 1–10; `NULL` = not yet scored. |
| `score_analyzed_at` | `TIMESTAMPTZ NULL` | Set by `analyzeGaps` when score is written. Compared against `updated_at` to detect staleness. |

Migration file: `supabase/migrations/007_section_readiness_score.sql` (number TBD when applied — see [[Database]] conventions).

```sql
ALTER TABLE brief_sections
  ADD COLUMN readiness_score INTEGER NULL
    CHECK (readiness_score IS NULL OR (readiness_score BETWEEN 1 AND 10)),
  ADD COLUMN score_analyzed_at TIMESTAMPTZ NULL;
```

No RLS changes needed — `brief_sections` already inherits per-user access from `briefs`.

## AI / Prompt Design

Extend `GAP_ANALYSIS_TOOL` in `briefly/src/lib/ai/gap-prompts.ts` so each section item in the tool-use output includes a `readiness_score` field.

> [!info] Tool schema addition
> Add `readiness_score: { type: "integer", minimum: 1, maximum: 10 }` to the per-section object schema, and mark it required.

Update `buildGapAnalysisMessage` to instruct Claude on scoring semantics:

- **10** — Section is complete, specific, internally consistent, with no gaps of any severity.
- **7–9** — Strong section; minor nice-to-haves or small specificity wins remain.
- **4–6** — Usable but thin or generic; one or more recommended gaps.
- **1–3** — Risky/incomplete; critical gaps present or content is missing/contradictory.

Scoring inputs Claude should weigh: content completeness, specificity, internal consistency, and the presence/severity of detected gaps. The score must be returned in the **same** tool call as the gaps — no separate request.

## Implementation Notes

Implement in this order:

1. **Migration** — add `readiness_score` and `score_analyzed_at` columns to `brief_sections`. Apply locally, regenerate Supabase types.
2. **Prompt** — extend `GAP_ANALYSIS_TOOL` schema and `buildGapAnalysisMessage` instructions in `briefly/src/lib/ai/gap-prompts.ts`. Update any TypeScript types for the tool-use payload.
3. **Server action** — in `analyzeGaps`, after Claude returns, extract `readiness_score` per section and:
   ```sql
   UPDATE brief_sections
   SET readiness_score = $1, score_analyzed_at = now()
   WHERE id = $2;
   ```
   The existing "wipe and re-insert gaps" pattern stays unchanged; the score update is a separate `UPDATE`.
4. **UI** — build `ReadinessBar` component (10-segment gradient bar). Wire into `BriefSectionCard` between the title and the content area. Also render on Step 6 Review view next to each section.
5. **Staleness** — compute `isStale = section.updated_at > section.score_analyzed_at` in the section card; pass to `ReadinessBar` for dim rendering.

> [!warning] Backfill
> Existing sections will have `readiness_score = NULL` until the user re-runs gap analysis. That is intentional — the bar simply stays hidden until then. Do **not** backfill with a default value.

## Acceptance Criteria

- [ ] Migration adds `readiness_score` and `score_analyzed_at` to `brief_sections` with the integer check constraint.
- [ ] `GAP_ANALYSIS_TOOL` schema includes `readiness_score` (integer, 1–10, required) per section.
- [ ] Claude returns a score for every section in every analysis run.
- [ ] `analyzeGaps` server action persists `readiness_score` and `score_analyzed_at` per section in the same transaction/flow as gap insert.
- [ ] `ReadinessBar` renders below section title in each `BriefSectionCard` after analysis.
- [ ] `ReadinessBar` also renders on Step 6 Review view.
- [ ] Bar is hidden when `hasAnalyzed === false` or `readiness_score IS NULL`.
- [ ] Bar uses red→amber→green gradient with the filled-segment count equal to the score.
- [ ] When a section is edited after analysis, the bar renders at reduced opacity with a "stale" indicator.
- [ ] Re-running gap analysis refreshes both the score and `score_analyzed_at`, clearing the stale state.

## Open Questions

- Should the numeric score (`7/10`) be visible by default, or only on hover? Default-visible is assumed.
- Do we want a single aggregated "brief readiness" score on the Review view (average of sections)? Out of scope for this iteration but worth revisiting.
- Should the bar be clickable to jump to a re-analyze action? Probably not — Step 6 already owns that affordance.
